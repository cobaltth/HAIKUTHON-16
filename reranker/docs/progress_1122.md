### 사실

### 이유 (계산)
- 6장 안에 정답이 있을 확률은 약 .49다(R@5 .434에 한 장 더). R@1 .2609 ÷ .49 ≈ **.53**. 정답이 후보 안에 있어도 Qwen이 1등으로 올리는 것은 절반뿐이다. val에서는 .90이었다.
- 후보가 k장일 때 정답률을 `p^(k−1)`로 보면(p = 오답 후보 하나를 이길 확률):
  - v4: 3.9장에서 .71 → p ≈ .889
  - v6a: 6장에서 .53 → p ≈ .881
  - val: 5장에서 .905 → p ≈ .975
- 두 제출이 같은 p(약 .885)를 준다. 즉 **테스트에서 Qwen은 형제 그림 하나당 11.5%의 확률로 진다.** val에서는 2.5%였다. 테스트 형제가 4~5배 어렵다.
- 이 p로 R@1을 계산하면(순위당 정답 확률 .08 가정): k=4 .222, k=6 .261, **k=8 .272(최대)**, k=10 .266. 후보를 더 봐도 R@1은 오르지 않는다. 한 장 더 볼 때 얻는 recall만큼 새 오답 후보에게 진다.

### 형님 BLIP-2도 같은 수준이다
- 02(k=5): R@1 .2725 ÷ R@5 .4644 = .587 → p ≈ **.875**.
- Qwen LoRA(.881)와 BLIP-2 ITM(.875)은 테스트에서 형제를 가르는 능력이 거의 같다. 어느 한쪽을 더 깊게 돌려도 0.33 근처에서 막힌다.

### 결론과 방향 전환
1. **Qwen에게 후보를 더 많이 보여 주는 방향은 접는다.** A-2(이미지 먼저 프롬프트 + 재학습)는 하지 않는다. 이유: 위 계산에서 k를 6→10으로 올려도 R@1이 +.01 이하.
2. **남은 레버는 "한 쌍을 더 정확히 판정하기"다.** 가장 가까운 방법은 서로 다른 두 판정기(BLIP-2와 Qwen)의 점수를 같은 후보에서 합치는 것이다. 이유: 둘의 정확도가 같고 구조가 달라서, 오류가 겹치지 않는 만큼 p가 오른다. p가 .88 → .92가 되면 5장 기준 정답률이 .59 → .72, R@1 .27 → 약 .33이다(추정, 오류가 얼마나 겹치는지는 아직 모른다).
3. **3단 구조의 가치는 "깊이"가 아니라 "두 판정기의 결합"에 있다.** 그래서 권고를 바꾼다: K1을 20~30으로 키우는 것보다, **1단계 top-5에 BLIP-2와 Qwen을 둘 다 돌려 점수를 합치는 것**이 우선이다. BLIP-2 k=5는 386초로 검증돼 있다.
4. **v7(비전 특징 재사용)의 목적을 바꾼다.** 더 많이 보기 위해서가 아니라, BLIP-2와 같은 예산 안에 Qwen 5장(40,000쌍)을 넣기 위해서다. 지금 속도(13ms)면 Qwen만 520초라 386 + 520 = 906초로 넘친다. v7로 쌍당 8~9ms가 되면 약 720~750초로 들어간다(추정).
5. 1단계 점수도 최종 결합에 넣는다. 지금 v6a는 Qwen 점수만으로 순위를 정한다. 형님 방식(재정렬 점수와 1단계 점수의 가중합)이 테스트에서 통했다.

## 민서님 앙상블 zip(k1=15, k3=3) 평가와 권고 (01:41)
- 좋은 점: BLIP-2 → Qwen → 표준화 후 가중합 구조, 1·2위부터 처리하는 순서, 설정 숫자만으로 k1·k3 변경 가능.
- 고칠 점과 이유:
  1. Qwen 쌍당 20ms는 256px 기준이다. **192px면 약 13ms**(v6a가 서버에서 48,000쌍 포함 799초에 끝남). 40,000쌍이 800초가 아니라 520초다.
  2. **k1=15는 Qwen이 돌 시간을 없앤다.** 형님 실측: k=5 386초, k=20 721초 초과 → k=15는 최소 610초, 아마 700초 이상(추정). 가드 840초에서 Qwen에 남는 것은 많아야 230초로, 1·2위 비교 한 번(16,000쌍 = 208초)도 빠듯하다.
  3. **BLIP-2를 깊게 돌리는 것 자체가 이득이 없을 가능성이 크다.** 테스트에서 BLIP-2는 형제당 12.5% 확률로 진다. 후보가 늘면 정답이 들어올 확률보다 새 형제에게 질 확률이 빨리 커진다(v6a에서 Qwen이 4장 → 6장일 때 R@1 +.004). 1단계 점수를 섞는 것이 얼마나 막아 주는지는 모른다.
  4. **val 비교는 깊은 쪽에 유리하게 나온다.** val은 형제당 오류 2.5%라 깊을수록 항상 오른다. 테스트는 11~12%다. val 결과로 k1을 고르면 안 된다.
  5. Kaggle T4에서 Qwen이 느린 것은 T4가 bf16을 가속하지 못해서다(우리 로더는 bf16으로 복원). 서버는 L4라 문제없다. 속도는 Colab L4에서 잰다.

## 제출 04: 형님 k=20 — 가드에 걸려 재정렬이 반영되지 않음
- R@5가 02와 소수 넷째 자리까지 같다(3715/8000) → 모든 질의의 top-5가 1단계 top-5 그대로. 시간 12:01 = 721초 = 형님 가드 720초. 점수 .232 = 스타터 키트 단독(약 0.23).
- 결론: **k=20은 평가되지 않았다.**
- 알게 된 것:
  1. BLIP-2 k=20은 12분 안에 끝나지 않는다. ITM 16만 쌍이 예상보다 비싸다(내 추정 9~10분이 틀렸다).
  2. 형님 가드는 걸리면 재정렬을 통째로 잃는다 → 순위 묶음(1~5, 6~10, …) 순서로 ITM을 돌리고 완료된 묶음까지만 쓰도록 권고함. 이유: 시간이 모자라도 k=5 결과(0.3275)가 보장된다.
  3. FT한 SigLIP-base 단독: R@1 .153, R@5 .464, 점수 .232.
- 05 판정을 반영하면, 형님 k=10도 큰 상승은 기대하기 어렵다(p .875로 계산하면 k=5 .27 → k=8~10 .28~.29, 추정). 그래도 한 번 확인할 가치는 있다. 이유: 형님은 최종 점수에 1단계 점수를 섞기 때문에 위 계산보다 나을 수 있고, 3단 구조의 K1을 정하는 근거가 된다.

## v7: Qwen 비전 특징을 이미지당 한 번만 계산
- 근거: 쌍당 시간 실측 256px 20.2ms / 224px 16.8ms / 192px 13.9ms를 직선으로 맞추면 `5.8ms + 0.056ms × 패치 수`. 192px에서 이미지 몫 약 8.1ms, 질의 몫 약 5.8ms.
- 기존 `model.py`는 쌍마다 이미지 전처리와 비전 인코더를 다시 돌린다(코드 확인). 48,000쌍에 이미지는 최대 16,000장이다.
- transformers 5.22.2의 `Qwen3VLModel.forward`는 `mm_encoder_outputs={"image": obj}`를 받는다. `obj.pooler_output`(이미지별 임베딩 튜플)과 `obj.deepstack_features`(층별 튜플 리스트)가 필요하고, `lm.model.get_image_features(pixel_values, image_grid_thw, return_dict=True)`가 만든다. 위치 계산에 `mm_token_type_ids`(이미지 토큰 = 1)와 `image_grid_thw`가 필요하다.
- 변경점: (1) 패스별로 필요한 이미지만 비전 인코더 통과 후 GPU 캐시, (2) 텍스트 직접 토크나이즈(`<|image_pad|>`를 토큰 수만큼 확장, 왼쪽 패딩), (3) 패스 안 질의 길이순 배치, (4) 시작 시 8쌍을 기존/새 경로로 모두 계산해 차이가 `vc_tol`(0.5)을 넘으면 기존 경로로 전환, (5) 예외 시 남은 쌍은 기존 경로.
- 새 cfg 키: `vcache`, `vc_batch` 32, `vc_img_batch` 64, `vc_tol` 0.5, `len_sort`. `m["_timing"]["vcache"]`에 used / ids_match / check_diff / images / t_vis / t_lm 기록.
- 캐시 메모리 추정: 192px에서 이미지당 약 0.59MB, 16,000장이면 약 9.4GB(실측 필요).
- **검증 결과 (01:50, Colab L4, valA 800질의 × 1600장, k=6 전부, 192px)**:
